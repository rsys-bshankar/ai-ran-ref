# Validation program (v0.5.0)

What is tested today, by category, what is not, and the order in which the gaps are closed in 0.5.0. Every step is one PR with a CI lane, a recorded result and a line in `CHANGELOG.md`; a step that finds a defect fixes it in the same PR and says so (revision `0026` is the example: a staged CM job failed on Postgres for two releases because no test ran one there).

A lane is **gating** (every PR, under 25 minutes) or **nightly** (scheduled and by hand, results kept as a workflow artifact and summarised in the run). Load, stress, soak and the external-facing security scans are nightly: they are slow and noisy, and a gate that is flaky teaches people to ignore it.

Counts are test functions (`def test_`) at the time of writing: about 1,830 in the module and shared suites, 204 in `tests_integration`, 4 GUI files. The unit and integration suites run on SQLite, which hides every Postgres-only behaviour (check constraints, schemas, roles, locks, `SKIP LOCKED`): the Postgres lanes below exist because of that.

## 1. Unit tests
**Today**: 22 suites. By count: RAN NF OAM 384, shared 225, AIMgF 181, SDK 119, SME 106 at the top; MLLF 6, RAN Analytics 13, SO SMOS 15, mock O1 adaptor 23, SA SMOS 28 at the bottom. Lint is `ruff` for syntax errors and undefined names only.
**Measured (V-1, statement coverage of each module's own unit suite on SQLite)**: the modules are at 93 to 100 % (the small ones by count are fully covered: MLLF 100 % of 26 statements, RAN Analytics 100 %, SO SMOS 100 %), `shared` 87.5 % (its Postgres tests skip in this job and run in `migration-postgres`), SDK 96 %, GUI backend 94.7 %. Two findings: (1) **a low test count is not low coverage**, so "thin" in the first draft of this plan was the wrong measure and the per-module test-raising work is dropped; (2) the four **sample rApps' own suites covered only 37 to 48 %** of their `app/` code (the model and decision engine, not the service routes, which the integration tests and the runbook exercised; raised to 98 to 99 % by V-2k, below), and **R1 Termination reads 84.5 %** although a line tracer shows its proxy path running: coverage.py under-reports the async handler there, so the number is a lower bound and the floor is set at what is measured.
**Gaps**: no mutation testing, so no evidence that the tests would notice a change; `tests_integration` is not type checked; the gateway is measured only indirectly.
**Plan**: **V-1** (done) coverage runs in the SQLite job for every suite (`scripts/run_unit_suite.sh`), and `scripts/coverage_floor.py` fails a module below its floor in `coverage_floors.json` and one more than 3 points above it (raise the floor in the same PR), so coverage can only go up. **V-2a** (done) `ruff` runs the bug-finding rule sets `B` (bugbear), `S` (bandit) and `PLE` as well (`ruff.toml` says what is switched off for which kind of file and why; the 21 raises that lost their cause now chain with `from`, the other findings are fixed or carry a reasoned `noqa`). **V-2b** (done for `shared/`) `mypy` runs in the `lint` job on the shared library (`shared/mypy.ini`, with `check_untyped_defs`); what it found is fixed (a possibly missing outbox row, a damaged idempotency row, an `Optional` secret, a wrong generator annotation, and the rest). **V-2d** (done, `scripts/run_mypy.sh`, in the `lint` job) all nineteen modules are clean under the same settings and checked (V-2e added SA SMOS, the mock O1 adaptor and FOCOM, V-2f the GUI backend, V-2g AIMgF, V-2h Intent Service, V-2i RAN NF OAM, V-2j the SDK). **V-2c** (pilot done, `scripts/mutation_pilot.sh`, `.github/workflows/smo-mutation.yml`, weekly) `mutmut` on the role policy and enrollment-secret check, the rate limiter, pagination and the time helpers: of 131 mutants the existing tests killed 49, 5 survived and 77 were reached by no test of the shared library. What that showed: the table of rate-limit buckets was never tested for being cleaned up (so it could grow without bound), `as_utc` was never given an already-aware value (a version that stamped UTC on everything passed), and `enrollment_secret_valid`, `role_of` and `paginate` had no direct test. Tests for each were added and all 131 are killed; the run fails if one is not. Extending it (the gateway's routing, SME's token checks, the audit chain) is the next step, a module at a time. **V-2k** (done) the four sample rApps' routes run under their own tests (`samples/<name>/tests/test_routes.py`: FastAPI's TestClient on SQLite, the SDK and R1 replaced by an in-memory platform double that keeps a cell-configuration store, so a write, its read-back, a rollback and a KPI-verified revert are the real code paths over the real model and decision engine; every route's success path, the 404/422/409 and platform-error paths, the SHADOW, ASSIST and AUTONOMOUS paths, and the Digital Twin producer's routes), which took their coverage from 37-48 % to 98.6-98.9 % (floors 98); and the four are under `mypy` (`scripts/run_mypy.sh`, 83 findings fixed with annotations, `get_one` and a few reasoned `cast`s, no change of behaviour, the packages rebuilt). Still to do under V-2: `tests_integration` under `mypy` (103 findings in 23 files, mostly the importlib `spec.loader` idiom and untyped test doubles; the sample rApps' and modules' own tests are not type checked either).

## 2. Integration tests
**Today**: `tests_integration` (204): the in-process mesh replays DEMO_RUNBOOK §2-§27, authorisation and role walks over every route, compose/Helm consistency, probes and `/version` on every service, the configuration reference (every environment read is in `docs/CONFIGURATION.md`, with a seeded-miss test), graceful shutdown. The same runbook replays against the live compose stack, behind PgBouncer, and against two replicas of every module.
**Gaps**: nothing replays the runbook through a restart, a failover or a slow dependency (HA below); the sample rApps run as static services in compose, not deployed through `POST /instances`.
**Plan**: folded into HA and failure injection (V-8, V-9).

## 3. Interface tests (R1, O1/O2, NETCONF, northbound)
**Today**: OpenAPI specs generated per service and checked against the live schema; a real NETCONF server (Netopeer2) in CI for SSH and TLS sessions; the R1 gateway's role and audit behaviour in the roles script.
**Gaps**: nothing checks that a service answers what its own spec says (status codes, response shapes) on arbitrary valid input; nothing detects a breaking change between releases (QA-2); the O1 YANG models of WG4 are not bundled.
**Plan**: **V-3** (seventeen modules done, gating) schemathesis over each module's live OpenAPI, in process on the integration mesh (QA-2.1; QA-2.3 continues): every in-scope module passes (the mock O1 adaptor's NETCONF and RESTCONF protocol routes are waived with a reason, since an OpenAPI/JSON check does not describe an XML or RESTCONF stub). Findings fixed on the way: unknown ids answering 500 (A1 policies, NFO, SO SMOS, SA SMOS, RAN NF OAM), duplicate registrations answering 500 (EI type, O1 adaptor, intent handling function), numbers too large for a column (every module now answers 422 `VALUE_OUT_OF_RANGE`), malformed steps and changes, a DME action behind a failing RAN NF OAM; and the spec now declares the error bodies. A 502/503 with a ProblemDetails body is accepted as a deliberate dependency failure. A1 and the mock Near-RT RIC were removed (out of scope, `OPEN_ITEMS.md` "Scope"), so they are not covered. Note: the run order matters slightly, since the modules share one test database. **V-4** (done, gating, `scripts/check_breaking_changes.py`; the deprecation policy is in `docs/RELEASES.md`) a breaking-change check: the spec of the previous release tag against this one (removed or narrowed routes, new required fields) as a gating job with a waiver file; consumer-side checks for `R1Client` calls (QA-2.2, done: `tests_integration/test_r1_consumer_calls.py` reads every literal-path call with `ast` and checks the route prefix, the method and path, the body fields and the query parameters against the producer's spec; computed paths are skipped and counted, deliberate exceptions are in `r1_consumer_waivers.json`). Both feed the deprecation policy of the 1.0 work.

## 4. Database tests
**Today** (Postgres lanes): fresh and legacy databases reach one schema; the previous release's schema upgrades to head; the previous release's code runs on this schema; every revision up and down; per-module roles can use their schema and nothing else (all 22 roles); concurrency, idempotency and outbox claim under real Postgres; backup and restore round trip (compose); the off-site backup and the restore drill against MinIO with the RPO and RTO gates (`.github/workflows/smo-dr.yml`, `scripts/dr_drill.sh`, `docs/DISASTER_RECOVERY.md`); slow-statement log; password rotation.
**Gaps**: **the other ~100 CHECK constraints against the code that writes them** (the class of defect behind 0026); no query-plan or index test on realistic volumes (DB-4); retention is built but its purges are tested on SQLite only, not against Postgres at volume (DB-3, `docs/RETENTION.md`); a restore drill on a real stack at representative size (DB-6.4, HA-6.3: the CI drill is small), the WAL archive of CloudNativePG (never run in CI), and an alert on a late backup; the upgrade over a large table is timed per revision (`scripts/upgrade_at_volume.py`, in the volume workflow: the previous release's head to this checkout's, with a budget).
**Plan**: **V-5** (done, `tests_integration/test_check_constraints.py`) every single-column CHECK list compared with the state-machine enum of its column and with the literals the owning module assigns; Postgres only, gating. It found nothing beyond `0026` and was shown to fail on the pre-`0026` schema and on a seeded literal. The Postgres-only tests of `tests_integration` had not been running in CI at all (they skip without `SMO_TEST_POSTGRES_URL`); they now run in the `migration-postgres` job. **V-6** (first slice done, `.github/workflows/smo-db-volume.yml`, `scripts/db_volume_check.py`) a million alarms and half a million performance files on Postgres 18, `EXPLAIN` assertions on the list routes' queries and a timed dump/restore drill (6 s and 9 s for 51 MB, counts equal). It found a missing index on `pm_file`, unstable paging and an unordered operation history (fixed, migration 0027). The page total's `COUNT(*)` is reported (linear) and every list route has the opt-out `?total=false` (no count, `hasMore`). Still to do: the migration of a large table (timed), retention (DB-3), the runbook replay after a restore (DB-6.2; the host-mode backup against Postgres 18 now runs in the `disaster-recovery` job).

## 5. Penetration and security tests
**Today**: CodeQL (Python, JS, Actions), dependency review, Trivy image scan with a severity gate, two fuzz targets (CSAR parsers, webhook guard) in ClusterFuzzLite, Scorecard, secret-handling tests, the gateway authorisation walk, TLS edge tests, mutual TLS between services (certificate script and rotation phases, a real handshake that refuses a client with no certificate, one from another CA and plain HTTP, and the CI job `compose-mtls` that replays the runbook over mTLS: `tests_integration/test_mtls.py`, `shared/tests/test_mtls.py`, `scripts/compose_mtls_check.py`), SSRF guard tests on callback URLs, and the erasure of a GUI user tried once end to end (`gui-bff/tests/test_main.py::test_erasing_a_gui_user_end_to_end_and_what_it_leaves_behind`, `docs/PRIVACY.md` section 4). `docs/CONTROL_MATRIX.md` maps this evidence to ISO/IEC 27001:2022 Annex A themes and NESAS/SCAS test categories and names what is not tested. No active scan of the running stack, and no external test.
**Gaps**: no DAST against the live stack; no check of the TLS configuration from outside; no abuse tests of the token flow (replay, algorithm confusion, scope escalation, enrollment-secret guessing, rate-limit bypass); no brute-force protection test of the GUI login; the scope for an external penetration test is unwritten (SEC-14.4).
**V-7** (done, nightly, `.github/workflows/smo-dast.yml`, `security/README.md`) OWASP ZAP API scan of the gateway driven by its OpenAPI document, `testssl.sh` against the TLS edge and a Nuclei run of the default template set, each with a baseline file of accepted findings in `security/`; new findings fail the run. **V-7d** (done) ZAP again with an access token (job `dast-authenticated`): each of the 15 modules' own OpenAPI documents called through the gateway (`scripts/dast_gateway_spec.py`), as an rApp and as an SMO module (`scripts/dast_token.py`); same baseline file. Its first runs found four defects, all fixed in the same pull request: an unknown element read as a 503 (`/config`) and as a 500 (FM and PM subscriptions, a foreign key), an application type the column refuses as a 500, and the plain-text body of every unhandled 500 (now a problem document). Not yet: a scan of each module on the internal network. **Plan** for the rest: **V-7b** (done, gating, `tests_integration/test_token_abuse.py`; it found the dot-segment bypass of the role policy, now closed at the gateway) a token-abuse suite in `tests_integration` (replay, expiry, scope, wrong audience, none-algorithm, SQLi and path traversal on every path parameter via the route walk). **V-7c** (decided) the in-repo DAST above is built regardless (V-7, V-7b), so the obvious findings are gone before a human looks. The **external penetration test is a criterion for 1.0.0, not for 0.5.0**: it is commissioned after the security hardening items (mTLS, OIDC, MFA and revocation, `/bootstrap` exposure) and against the 0.5.0 release candidate or later, so the testers see the stack that ships. The one-page scope and rules of engagement (SEC-14.4) are the draft `docs/PENTEST_SCOPE.md`.

## 7. Stress, soak and failure injection
**Today**: HA lanes kill a worker, the job runner and the Postgres primary on kind and measure the write gap; nothing pushes past capacity.
**Plan**: **V-9** (SME down and the slow or dead subscriber are done: `stress_run.py probe --down-status 503`, `shared/tests/test_outbox.py`; the limiter's shared state, `R1_RATE_STORE=postgres` (SEC-8.5), is proved at the statement level by `tests_integration/test_rate_limit_postgres.py`, Postgres only, in the `migration-postgres` job: three replicas with their own pools get exactly one burst, and `shared/tests/test_ratelimit_shared.py` covers the fail-open path; and under load: `stress_run.py limiter-shared`, three gateway replicas, a burst of 120 calls: with each replica's own buckets several budgets get through (the control), with `R1_RATE_STORE=postgres` about one, and a count of the requests each replica answered keeps a burst that reached one replica from passing for either) stress on the V-8 harness: ramp to saturation, then hold (pool exhaustion must give 503 with `Retry-After`, never a hang or a wrong answer), burst past the R1 rate limiter, oversized bodies, a slow or dead webhook subscriber (QA-3.3), Postgres slow (`pg_sleep` injection) and unreachable (QA-3.1), SME down (QA-3.2), disk full on the package volume (no scenario yet: `smo_packages` is mounted on onboarding at `/srv/packages` but nothing writes to it, since a CSAR is fetched, validated in memory and only its manifest is stored in the database; the scenario is written when something does persist packages). **V-9b** a soak (nightly 6 h, release-candidate 24 h/72 h by hand: QA-5): memory, pool, file descriptors and outbox depth must be flat.

## 9. Rollback tests

**Gaps**: a migration that fails in the middle of a revision that changes data (only a blocked one is exercised: the whole migration is one transaction, so the effect is the same, but a revision's own error is not); downgrade of the full chain from head with data, not one step.

## Order, and what each step must leave behind
1. V-5 (CHECK audit, done) and V-1 (coverage, done): cheapest. V-5 found no second 0026 but showed the Postgres-only tests were not running in CI.
2. V-3/V-4 (contract and breaking-change): needed by the 1.0 deprecation policy.
3. V-8 (load harness) then V-9 (stress/soak): the numbers everything after compares against.
4. V-10/V-11 (upgrade and rollback on kind), V-12 (multi-node HA).
5. V-13 (GUI browser tests), V-7 (DAST and token abuse; V-7c is decided: the external test is a criterion for 1.0.0).
6. Release candidate: every lane green, the 24 h soak run by hand, `docs/PERFORMANCE.md` and the waiver files reviewed, then Release 0.5.0 with the criteria for 1.0.0.

Every PR records: what was run, against what, the numbers, defects found and where fixed, and what remains untested. A lane that was never red is not evidence until it has been shown to fail on a seeded defect; each new test says how that was checked.
