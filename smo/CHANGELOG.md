# Changelog

All notable changes to the SMO. Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versioning and how a release is cut: `docs/RELEASES.md`.
Entries are written for an operator: what changed in behaviour, configuration or the schema. The design record is `HISTORY.md`; what is still open is `OPEN_ITEMS.md`.

## [Unreleased]

### Removed
- **A1, the Near-RT RIC and E2 are out of scope at every stage, and what implemented them is gone.** Removed: the `a1-related` module (A1 policy management, the A1-P service registry and A1 EI types) and `mock-near-rt-ric`; the `/a1-related` route of the gateway (now `404 NO_ROUTE`) and its role-policy and GUI-permission entries; their compose services, secret `db_password_a1-related` and network `a1_mock_net`, their Helm modules and the chart's `networkPolicy` (its only rule isolated the mock RIC); `A1_RELATED_URL`; their specs (`docs/openapi/a1-related.json`, `mock-near-rt-ric.json`), call flow 05 and demo runbook steps 11 and 22 (the other steps keep their numbers); the SO SMOS dispatch of `POLICY` / `A1_RELATED` steps (such a step now fails as having no dispatcher); in the GUI the A1 policies, policy status subscriptions, A1 services and A1 EI types tabs, call flow 05 and the A1 tile of the dashboard (the page "Policy & Intents" is now "Intents", at the same address); and the `OI-5-a1-*` open items. The code is in the tag `smo-v0.4.0`; `OPEN_ITEMS.md` keeps A1 as a future work item.
  Upgrading: nothing consumed A1 outside this repository (no sample rApp used it). The four tables (`a1_ei_type`, `a1_policy`, `a1_service_registration`, `policy_status_subscription`, in the schema `a1_related`) and the role `smo_a1_related` stay in an existing database, unused: the release that removed the code cannot drop what the previous release still uses (a rolling upgrade runs both), so a later revision drops them, and until then they are listed under `_retired` in `migrations/table_owners.json`. An operator who does not need the previous release any more can drop them, the schema and the role by hand. The Helm values `modules.a1-related`, `modules.mock-near-rt-ric` and `networkPolicy` are gone: delete them from your values file.

### Fixed
- **Deleting a GUI user now also removes its failed-login counter, and a user created again under the same name no longer accepts the old person's tokens (found while writing the erasure procedure, STD-4.3).** `DELETE /api/admin/users/{username}` removed the account and left the `gui_login_failure` row kept under that name; both go in one transaction now. A user created after a deletion started at session-token version 0 and so accepted an unexpired token the previous holder of the name had been issued; a new user now starts at a random version. Existing users and sessions are unaffected. The audit rows that name a deleted user are kept (append-only), as are the names the GUI wrote into module records: `docs/PRIVACY.md` says which and what the options are.
- **A destination that does not answer no longer holds up the other notifications (found while writing the subscriber stress case, V-9).** `smo_shared.outbox.drain` sent the due rows one after the other, so every row behind a dead or hanging subscriber waited out that subscriber's two-second timeout (a sweep over 100 rows to a dead destination took over three minutes, during which healthy subscribers got nothing). The claimed rows are now sent concurrently (`SMO_OUTBOX_SEND_CONCURRENCY`, default 8); the claiming, the retry/backoff and the lease are unchanged. A test with eight hanging destinations and one healthy one shows the healthy one delivered at once.
- **Logging out of the GUI now ends the session itself; a copied cookie or token stops working (found while designing the browser session checks, V-13).** `POST /auth/logout` only deleted the browser's cookies, so a session token that had been copied stayed valid until it expired (8 hours by default). Each session now carries an id (`jti`); logout records it in the new table `gui_revoked_session` (created at startup like the backend's other tables, entries forgotten once the token would have expired anyway) and every later request with that token is `401 SESSION_REVOKED`. Works for the cookie and for a Bearer token, and across several backend replicas (the table is shared). A token issued before this release has no id and still lives until it expires.
- **`scripts/migrate.py` leaves a database at a later release's revision alone (found by the rollback lane, V-11).** A `helm rollback` to the revision made by `helm install` re-creates that install's plain migrate Job, which ran the older image's `migrate.py` against the newer schema and failed with "Can't locate revision". A revision the image does not know is a later release's, which this image runs on (expand and contract): there is nothing to upgrade, and it now says so and exits 0. The images of releases before this one still fail in that case, so roll back to a revision made by `helm upgrade` (its migrate Job is a pre-upgrade hook, not run by a rollback): the lane does, and the chart's README ("Rolling back") says so.
- **Lists at volume (found by the volume lane, V-6).** A million alarms and half a million performance files showed three things: (1) the performance files of one managed element scanned the whole table (27 ms and growing); migration `0027` adds the index (`alarm` had it). (2) Every list route paged with no ORDER BY, so a database could return two pages' rows in different orders and a row could be on both pages or neither; `smo_shared.pagination.paginate` now orders an unordered statement by its primary key (a route that orders itself is untouched). (3) A deployment's operation history (NFO `/deployments/{id}/operations`) had nothing to order it by; `lcm_operation.created_at` (migration `0027`, default now()) now orders it, oldest first. Not changed: the page `total` is still a `COUNT(*)` of the whole result, 55 ms for a million alarms (linear: about half a second at ten million); it is reported by the lane, and `?total=false` (above) skips it. The previous release's code runs on the new schema (an index, and a column with a default).
- **`helm rollback` to the previous release failed because the role-password Secret lost a module's key (found by the upgrade lane, V-11).** The Secret `smo-role-secrets` was re-made on each upgrade from the modules the release knows, so after the upgrade that removed A1 it had no `db-password-a1-related`, and the previous release's chart, which still mounts it, could not start its pods or its migrate Job. A password the release has no role for is now carried forward.
- **With SME or its database down, the gateway answered every caller 401 `UNAUTHORIZED`; it now answers 503 `AUTH_SERVICE_UNAVAILABLE` with `Retry-After: 5` (found by the stress run, V-9).** The token check asks SME whether the token is active; when SME did not answer (unreachable, or an error of its own) the gateway read that as a bad token. Still fail-closed (nothing is forwarded), but a client that reads a 401 drops a good token and signs in again, into the same outage; a 503 with `Retry-After` is what a client retries. A token SME says is not active is still a 401.

### Added
- **`?total=false` on every list route skips the count of the whole result.** The `COUNT(*)` behind `total` is linear in the result (55 ms for a million alarms, found by the volume lane, V-6). Every route that pages with `limit` / `offset` now takes an optional boolean `total` (default `true`: the response is exactly what it was). With `total=false` no count query runs, the response has no `total` and has `hasMore` (`true` when a row follows the page) instead; a client that reads `total` must not send it. Added to the 100 list routes of all modules by the one shared parameter, and to the operator GUI backend's `/api/admin/audit`; the response envelopes are not declared in the specs and the added parameter is optional, so no waiver is needed. In the specs the parameters of these routes are listed in a new order (`offset`, `limit`, `total`); nothing else changes.
- **Alerts, SLOs, runbooks and business metrics (OBS-4, OBS-5, OBS-7).** `deploy/helm/smo/files/smo-alerts.rules.yaml` is a Prometheus rule file with 18 alerts (module down, 5xx and latency, outbox backlog and dead rows, pool, audit write failure, outbound failures, rate limiting, refusals, worker tasks, faulted rApps) and the burn-rate pairs for three SLOs, written up with their targets in `docs/SLOS.md` (all marked proposed: availability 99.9%, latency 99% under 1 s, outbox delivery lag); each alert's `runbook_url` is a page in `docs/runbooks/` (symptom, impact, diagnosis, mitigation, escalation). The chart renders the same file as a `PrometheusRule` with `prometheusRule.enabled=true` (default off, needs the Prometheus Operator; `prometheusRule.labels` for your selector). New series on every module's `/metrics`: `smo_refusals_total{module,reason}` (4xx by class), `smo_outbox_rows{module,status}` and `smo_outbox_oldest_pending_age_seconds{module}`; `smo_rapp_packages{state}` (onboarding), `smo_rapp_instances{state}` (rapp-mgmt), `smo_intents{admin_state}` (intent-service), read from the database at scrape time (cached 15 s, `SMO_BUSINESS_METRICS_TTL_SECONDS`; aggregate replicas with `max`). A worker counts its tasks (`smo_worker_task_runs_total`, `smo_worker_task_last_success_timestamp_seconds`) and serves them on `SMO_WORKER_METRICS_PORT` when set (default off). Not yet: the O1 write failure rule and the other business metrics of OBS-4 (`OPEN_ITEMS.md`). A CI test checks that every metric and label in a rule exists in the code and every runbook link resolves.
- **Standards and compliance documents (STD-2.1, STD-4.1, STD-4.3, STD-5.1, STD-6.1).** `specs/README.md` now carries the specification release table: the release or version of every spec in `specs/` and every spec the code cites, which module realises it, and where (the releases are mixed: TS 28.105 at 19.5.0, TS 28.104 and TS 28.312 at 20.0.0; versions of O-RAN documents that are not in `specs/` are recorded as "not recorded"). New: `docs/PRIVACY.md` (every place personal data can be stored or logged, retention today, who can read it, and the erasure procedure for a GUI user, tested once, with what it leaves behind and why); `docs/DATA_RESIDENCY.md` (where data lives and what leaves a site; the code has no telemetry); `docs/CONTROL_MATRIX.md` (ISO/IEC 27001:2022 Annex A themes and NESAS/SCAS test categories against what exists, with evidence and status). Things an operator should know that the inventory found: the GUI's own database (users, GUI audit log) is not part of `scripts/db_backup.sh` (`DB-6.5`); the GUI audit log is append-only in the application and not hash-chained (`STD-4.7`); the GUI web server's access log holds client IP addresses; the platform has no retention for most data (`DB-3`). `SECURITY.md` was brought in line with the code (hashed dependency lock, Dependabot, the `tls` profile, generated Postgres password).
- **The four sample rApps' HTTP routes are tested by their own suites (V-2k, `samples/<name>/tests/test_routes.py`).** EnergySaving, Mobility Optimization, Coverage Optimization and Traffic Steering each get 25 to 29 route tests (FastAPI's TestClient on SQLite, with the SDK and R1 replaced by a platform double that keeps a cell-configuration store): instance start (and its 404 and 422), the lifecycle (train, validate, emulate, deploy, and a failed training), the evaluate loop in SHADOW, ASSIST (waiting, enacted or rejected on reconcile) and AUTONOMOUS mode, a write that O1 does not apply and its rollback, a KPI-degraded revert and a confirmed change, the guards and the coordination with the other rApps, the operator override (EnergySaving), the relations view (Traffic Steering), the audit, cell and dashboard views, and the Digital Twin producer routes. Their coverage goes from 37-48 % to 98-99 % and `coverage_floors.json` holds 98 for each, so a route that loses its test fails CI.
- **The scope of 0.5.0 and the criteria for 1.0.0 are written down (`OPEN_ITEMS.md`, `docs/RELEASES.md`).** 0.5.0 adds mTLS between services (with the mesh option), OIDC login for the GUI, a shared rate limiter, `/bootstrap` exposure controls, traces (Tempo), business metrics, alerts and SLOs, log shipping, runbooks, `/version`, a configuration reference, measured sizing, a GitOps example, disaster recovery (RPO 15 minutes, RTO 1 hour) and the compliance documents; signing keys, the external-secrets example and the plugfest plan move to 0.6.0 or later. Every pull request now updates the documents it makes stale (`CLAUDE.md`). Documentation only.
- **Stress: the gateway with SME stopped (V-9, `stress_run.py probe --down-status 503`).** The nightly run now stops SME and requires 503 with `Retry-After` within the deadline, then 200 within 90 s of SME's return. Not yet here: a slow subscriber through a running stack and a full package volume.
- **Sessions and roles of the operator GUI are checked in a real browser, nightly (V-13c, `scripts/gui_session_e2e.py`, in `.github/workflows/smo-gui-e2e.yml`).** As viewer, operator and admin: the sidebar shows what the role may open, the cookies are `smo_session` HttpOnly / SameSite=Strict / Path=/api and unreadable by a script, `/api/admin/users` is 403 below admin and a write without the CSRF header is 403, signing out removes the session and the copied cookie is refused; five wrong passwords lock the account (429); with `GUI_SESSION_TTL_SECONDS=20` a session is refused after 22 s and the GUI returns to the sign-in page. `docker-compose.yml` passes `GUI_SESSION_TTL_SECONDS` to the backend (default 28800, unchanged).
- **The GUI backend's permission table is tested rule by rule and role by role (V-13b, `gui-bff/tests/test_rbac_matrix.py`, QA-6.2).** The test is generated from `RULES`: for every rule a concrete request is made from its pattern (each alternative of `(a|b)` and every module of the catch-all separately), and for viewer, operator and admin the decision must be made by that rule, allow its minimum role and everything above, and refuse everything below; a rule with a query condition must not decide without it. 611 cases. It found a rule that was never reached (the second copy of `POST /aimgf/feature-groups` inside an alternation, the same role as the first): removed, no behaviour change; the SPA's permission fixture is regenerated.
- **The database at volume: query plans, timings and a restore drill (V-6, `scripts/db_volume_check.py`, `.github/workflows/smo-db-volume.yml`).** Postgres 18 is migrated, loaded with 100 000 managed elements (a million alarms, half a million performance files) and the queries the list routes run are explained and timed: the alarm list of one element must use its index and answer in 100 ms, the first pages and totals have budgets, the rest (deep pages, severity filters, performance files) are reported. Then pg_dump, pg_restore into a fresh database and a row-count comparison, with the sizes and times in the job summary. No product code changed.
- **High availability on a three-node cluster (V-12, `.github/workflows/smo-ha-kind.yml`, `deploy/helm/smo/ci/kind-3node.yaml`).** Two replicas of every module that can have them, hard placement and disruption budgets on, spread over three worker nodes of a kind cluster; then a node is drained and one pod of each replicated deployment is killed with no grace period, while every replicated service is asked for `/health` through its Service (a call may fail once and be retried, never twice in a row). Checked: each replicated deployment's two pods sit on two different nodes before and after the drain, the drained node's pods return elsewhere, the gateway gate and the audit chain pass at the end. The node drained is one that holds neither Postgres nor a volume-holding single pod (onboarding, the GUI backend: single by design). No product code changed. Not yet here: a hard node loss, the whole runbook replayed through the disturbance, a zone failure.
- **A soak lane (V-9b, `scripts/soak_check.py`, `.github/workflows/smo-soak.yml`).** A steady load for as long as asked (weekly for two hours; by hand up to six, the most one job can run) with the gateway, SME and RAN NF OAM watched: memory and open file descriptors, database connections and notifications waiting in the outbox are sampled every minute, and the run fails if any of them grew between the first third and the last by more than 25 % and a floor (50 MiB, 50 descriptors, 10 connections, 100 notifications) or if the load saw errors. No product code changed. The 24 h and 72 h release-candidate soaks need a runner of your own (a job here stops at six hours).
- **Stress and failure-injection checks of the gateway, nightly (V-9, `scripts/stress_run.py`, `.github/workflows/smo-stress.yml`).** Four stated invariants: a burst past the per-caller budget gets 429 with `Retry-After` and never a 5xx; a body over the cap gets 413 and the gateway keeps answering; callers in flight ramped 20 to 200 get only 200, or 429/503 with `Retry-After`, never a hang or another 5xx; with Postgres stopped a database-backed route answers with a 5xx within the deadline, and recovers to 200 within 90 s of the database coming back. Still to add: a slow or dead webhook subscriber, SME down, a full package volume, and the soak (V-9b).
- **The load run seeds a database of a stated size first (V-8b, `scripts/load_seed.py`).** `elements` of 1000, 10000 or 100000 managed elements, each with 10 alarms and 5 performance files, are loaded before the load starts, so the list routes are measured against realistic tables. No product code changed.
- **A load harness (V-8a, `scripts/load_run.py`, `.github/workflows/smo-load.yml`, `docs/PERFORMANCE.md`).** A nightly run drives a weighted mix of the main gateway routes at a fixed concurrency from a container on the compose network and reports requests/s, p50/p95/p99 per route, container CPU and memory and Postgres connections. `docker-compose.load.yml` switches the gateway's rate limiter off for it (`R1_RATE_PER_SECOND=0`); the default is unchanged. No product code changed.
- **Every page of the operator GUI is opened in a real browser, and checked for accessibility, every night (V-13a, `scripts/gui_e2e.py`, `.github/workflows/smo-gui-e2e.yml`).** Chromium (Playwright) signs in as the admin against the compose stack and opens each page: it must render, the backend must not answer its calls with a 5xx or a 401, and `axe-core` must find no serious or critical WCAG 2 A/AA violation that `security/gui-axe-baseline.json` accepts with a reason. A screenshot of each page is kept as an artifact. `axe-core` is a pinned development dependency of the GUI.
- **A mutation-testing pilot on the shared library (V-2c, `scripts/mutation_pilot.sh`, weekly in `.github/workflows/smo-mutation.yml`).** `mutmut` changes the role policy and enrollment-secret check, the rate limiter, pagination and the time helpers one small step at a time and fails if a change goes unnoticed by the tests. The first run found what coverage hid: nothing tested that idle rate-limit buckets are forgotten (the table could grow without bound), `as_utc` was never given a timezone-aware value, and the enrollment-secret check, `role_of` and `paginate` had no direct test. Tests for all of it are added (no product code changed); all 139 mutants are killed (131 at first; the stable page order added eight).
- **Nightly dynamic security scans of the running stack (V-7, `.github/workflows/smo-dast.yml`, `security/README.md`).** The stack is started behind the TLS edge and scanned with the OWASP ZAP API scan (the gateway, from its OpenAPI document), `testssl.sh` (the TLS edge) and Nuclei (the default templates, severity low and above); a finding that is not in the baseline of accepted ones (`security/*-baseline.json`, each entry with its reason) fails the run, and every report is kept as an artifact. Not a merge gate. Not yet scanned: authenticated calls and each module on the internal network. `docs/PENTEST_SCOPE.md` is the draft scope and rules of engagement for the external penetration test, a criterion for 1.0.0.
- **Token and identity abuse tests against the gateway (V-7b, `tests_integration/test_token_abuse.py`).** The real gateway in front of the real SME, backends recorded: no, empty, malformed and wrong-scheme `Authorization`, guessed, forged (`alg: none`), altered, expired and offboarded-invoker tokens are all 401 and reach no backend; the identity, role and on-behalf-of headers a caller sends never reach a backend, and an rApp cannot pose as a module; and a walk over every route fills each path parameter with `.` and `..` to check that nothing the policy lets an rApp change resolves to a route it refuses (with a control that finds the escape below when the guard is switched off).
- **A change to the R1 contract is checked against the previous release (V-4, `scripts/check_breaking_changes.py`).** The CI job "R1 contract has no breaking change since the previous release" compares every `docs/openapi/<module>.json` with the one at the newest `smo-v*` tag and fails on a removed operation, a new required parameter or request property, a narrowed bound or enum, a changed type, or a response property lost; deliberate breaks are waived with a reason in `scripts/breaking_change_waivers.json`, which is emptied at each release. `docs/RELEASES.md` has the deprecation policy (announce in a MINOR release, keep working for at least one more, remove in a MAJOR). The first run found only the bounds added by V-3 (111 operations: a list `offset` above 2147483647 and `purge-stale` above 36500 days, which had made the module answer 500); they are waived with that reason.
- **Contract tests: eight modules answer what their own OpenAPI says (V-3, `tests_integration/test_contract_schemathesis.py`).** schemathesis generates requests from each module's spec and checks that no input gives a 5xx, that the status code and body match what the spec documents, and that the content type is right; every other module sits behind the in-process mesh, so a call a route makes to another module lands on it. Under test: SME, A1 Related, AIMgF, MDAF, MLLF, MLMR, Onboarding, RApp Management (`SMO_CONTRACT_MODULES` selects others; deliberate exceptions go in `contract_waivers.json`, a stale one fails). It found real faults, fixed here: `GET`/`PUT /policies/{id}` and `GET /policies/{id}/status` answered 500 for an unknown policy (now 404 `POLICY_NOT_FOUND`), registering the same EI type twice answered 500 (now 409), a list `offset` above 2^31-1, an SME `purge-stale` with a huge `unused_for_days` and a huge integer in any request body answered 500 (the first two are now bounded; **every module now answers 422 `VALUE_OUT_OF_RANGE` when a number is too large for the column it would be stored in**, which on Postgres was a `DataError` and a 500). **Every module's OpenAPI now declares the error bodies it really sends** (RFC 7807 ProblemDetails inside `detail`, a string from the framework, FastAPI's validation list) for 400, 401, 403, 404, 409, 413, 422, 429 and 503, the `/ready` 503 report, and RFC 6749 errors on SME's token endpoints; the committed specs in `docs/openapi/` are regenerated. Eighteen modules are under test (SME, A1 Related, AIMgF, MDAF, MLLF, MLMR, Onboarding, RApp Management, NFO, SO SMOS, SA SMOS, FOCOM, RAN NF OAM, DME, Intent Service, RAN Analytics, the mock O1 adaptor, R1 Termination; the adaptor's NETCONF and RESTCONF protocol routes are waived with a reason; the mock Near-RT RIC is not covered because A1 is out of scope). The gateway's own errors (401, 403, 404, 429, 502, 503, 504, top-level ProblemDetails) are now declared in R1 Termination's spec. More fixes it forced: unknown ids on NFO operations and placement, SO SMOS orders, SA SMOS monitor evaluation, RAN NF OAM config and software jobs and endpoint heartbeats were 500 and are 404; a SO SMOS step without `stepType`/`targetModule` or a RAN NF OAM change without `managedElementRef` is 422; registering a second O1 adaptor for one element, or an Intent handling function twice, is 409; an offer with no delivery method is refused; a DME action whose RAN NF OAM call fails answers 502 `UPSTREAM_FAILED`; RAN Analytics no longer builds a URL from an unescaped producer id. A 502 or 503 with a ProblemDetails body counts as a deliberate "dependency missing", not a defect. `schemathesis` is in `requirements/dev.in` and the lock.
- **Coverage is measured and cannot go down (V-1).** Every unit suite runs under coverage in the CI job `unit-and-integration` (`scripts/run_unit_suite.sh NAME DIR SOURCE PYTHONPATH`, `coverage` added to `requirements/dev.in` and the hashed lock), and `scripts/coverage_floor.py` checks each of the 26 suites against `coverage_floors.json`: below the floor fails, more than 3 points above fails too (raise the floor in the same change), a new suite without a floor fails. The table is in the job summary. Measured today: the modules 93 to 100 %, `shared` 87.5 %, SDK 96 %, GUI backend 94.7 %, R1 Termination 84.5 % (a lower bound: coverage.py under-reports its async proxy), the four sample rApps 37 to 48 % from their own suites (their routes are exercised by the integration tests and the runbook).
- **Every CHECK list on a column is tested against the code that writes the column (V-5, `tests_integration/test_check_constraints.py`).** Revision `0026` fixed two constraints that refused states the code uses; this checks the other 95 single-column lists of the schema. Ten state-machine columns must allow every value of their enum, and a string literal assigned to a checked column in the owning module's source must be allowed by a constraint of that module's tables (deliberate exceptions go in `check_constraint_waivers.json`, with a reason; a waiver that no longer matches fails too). No further mismatch was found. The test was shown to fail on the pre-`0026` schema (`write_config_job.status` lacks `HALTED`) and on a seeded unknown literal. **CI now runs the Postgres-only tests of `tests_integration`** (per-module roles, status constraints, this one) in the job `migration-postgres`: they skip without `SMO_TEST_POSTGRES_URL`, which only that job sets, so the SQLite job had never run them.

### Changed
- **`scripts/run_mypy.sh` also checks the four sample rApps (V-2k); `tests_integration` stays out.** Fixed with annotations, `get_one` and a few `cast`s that carry their reason: 83 findings, none changing behaviour (a possibly missing model, decision or timestamp that the code's own order of calls guarantees is now said in the type). `tests_integration` has 103 findings in 23 files at this point and is listed as not covered. The four packages (`.csar`) are rebuilt because their sources changed; an installed rApp's behaviour is the same. The package builder (`samples/build_csar.py`) now also leaves out tool caches (`.mypy_cache`, `.ruff_cache`), which a local type check had put into the packages.
- **Validation notes (V-9): the "full package volume" stress case is deferred with its reason.** The volume `smo_packages` is mounted on the onboarding module but no code writes to it (a package is fetched, validated in memory, and only its manifest is stored in Postgres), so there is nothing to fill; `docs/VALIDATION.md` says so. Documentation only.
- **The SDK is type checked, which completes the type checking of every module (V-2j).** All nineteen modules (the shared library has its own step) now pass `scripts/run_mypy.sh`, which the `lint` job runs, with the mypy version the lock pins. 88 of the SDK's 97 findings had one cause: `ensure_ok`, which every wrapper returns, was declared to return `dict | list | None` while each wrapper promises a `dict` or a `list[dict]`; it is now declared to return the route's JSON (`Any`), as the wrappers' own annotations already state. No behaviour change. Not covered by mypy: the sample rApps and `tests_integration`.
- **RAN NF OAM is type checked (V-2i).** Eighteen of nineteen modules are covered; only the SDK is left. Nothing behavioural beyond one exception type: where the code already relied on a row existing (the adaptor endpoint of a managed element, a write-config job or KPI schedule the scheduler just selected, the kill row just written, the root of a managed-object subtree) the read is `get_one`, so a row that is gone raises `NoResultFound` where it raised `AttributeError` (a 500 either way). The safeguard-refusal helper is typed as never returning, the MSAC rule lookup reads each row once instead of twice, and the rest are annotations and narrowing.
- **Intent Service is type checked (V-2h).** Seventeen of nineteen modules are covered; RAN NF OAM and the SDK are left. Nothing behavioural: the autonomy dispatch's stored JSON is validated into the strict Intent model with `model_validate` (the same validation as before, written so the checker can follow it), an intent with no stored negotiation report body no longer fails with a `TypeError`, and the scheduling-time validator reads each list once.
- **AIMgF is type checked (V-2g); `scripts/run_mypy.sh` now runs the mypy that the lock pins.** Sixteen of nineteen modules are covered; RAN NF OAM, Intent Service and the SDK are left. Nothing behavioural: rows that the code already relied on existing are read with `get_one` / `.one()` (a missing row is still a 500, as it was), the expired-jobs sweep's internal list is typed as what it holds, and one early-return is written so the type checker can follow it.

### Fixed
- **A staged CM job failed on Postgres the moment it paused after its first wave (since 0.2.0).** A job with `waveSize` goes to `HALTED` between waves, and one reverted automatically marks its applied sub-changes `REVERTED`; the status CHECK constraints written with the baseline allowed neither, so the request got a 500 (`violates check constraint "write_config_job_status_check"`) and the job stayed at wave 1. The unit tests run on SQLite, which does not carry the constraints, and the runbook uses single-wave jobs, so nothing exercised it until the failover test of PR-HA-4.2. Revision `0026` replaces both constraints; `tests_integration/test_status_checks.py` checks them against the states of the code on Postgres, and the migration round-trip test now compares constraint definitions across every schema (it looked only at `public`, so a revision that changed a module's table was invisible to it). If you ran staged jobs on 0.2.0 or 0.3.0 and saw 500s from `POST /config-jobs`, this is the cause; the job rows from those requests were rolled back, so there is nothing to clean up.
- **A stopped rApp's config job left no record.** Since 0.3.0 the gateway refuses every change by a stopped rApp, config jobs included, with 403 `RAPP_KILLED`, before RAN NF OAM sees it. RAN NF OAM is what records a refusal (`GET /safeguard-refusals`) and tells those subscribed to refusal events, so a config job refused at the gateway was neither recorded nor announced. The gateway now leaves `POST /ran-nf-oam/config-jobs` to RAN NF OAM, which refuses it the same way (403 `RAPP_KILLED`) and records it; every other change by a stopped rApp is still refused at the gateway. (It showed on the CI cluster once the gateway ran two replicas: with one, the gateway's 3 s cache of the switch was usually stale at that moment, so RAN NF OAM refused first.)
- **A notification whose first send failed was never retried.** The outbox (0.1.0 onward) leaves a row `PENDING` when the destination does not answer or answers 5xx, to be retried by a sweep, and the sweep had not been built: only the send made right after the commit ever ran, so a subscriber that was down for a moment missed that notification for good, and so did one whose sender died mid-send. Every worker (`ran-nf-oam-worker` in compose and in the chart) now runs the sweep (`outbox-sweep`, every 5 s, `SMO_OUTBOX_SWEEP_SECONDS`; `SMO_OUTBOX_SWEEP=false` turns it off): due rows are sent with the existing back-off (5 s, 30 s, 2 min, 10 min) and are `DEAD` after five attempts; a row claimed by a sender that died is sent again when its 60 s lease runs out. Delivery is at least once. If you ran no worker, run one.

### Added
- **Calls to a Service are spread over its replicas, checked on Kubernetes.** The CI job `helm` sends 80 calls (to a path that does not exist, which the service counts and answers 404; `/bootstrap` for the gateway) to each of eight replicated modules from inside the cluster and reads each replica's own request counter (`scripts/k8s_route_count.py`); every replica must have served at least 10. This is the kube-proxy spread (per connection); a client that keeps one connection open stays on one replica until it reconnects.
- **A staged CM job survives its job runner, proved on Kubernetes (PR-HA-4.2).** The CI job `helm` starts a three-wave job with a 20 s pause between waves, scales the worker to zero after wave 1, waits out the pause and checks the job has not moved (only the worker advances it), scales the worker back, and requires the job to complete with every sub-change applied once (`scripts/k8s_staged_job_failover.py`). The state is in the database, so nothing was needed in the product.
- **The runbook replayed against two replicas of every module (PR-HA-1.2).** `docker-compose.replicas.yml` (`docker compose -f docker-compose.yml -f docker-compose.replicas.yml up -d`) runs two containers of every module that can have them, the same list as the Helm `ci/ha-values.yaml` (Onboarding, the GUI backend and the mocks stay at one; the host ports of R1 Termination and the GUI are dropped). The CI job `compose-replicas` brings it up, checks that each has two running containers, runs the gateway role checks and the audit chain verification, and replays the whole runbook (§2-§27) with each module's callers reaching its replicas through Docker's DNS.
- **A connection pooler, in transaction mode (PR-DB-5.1 to 5.3).** The compose profile `pooler` runs PgBouncer (`pgbouncer/`, Alpine 3.22's package; users and passwords are built from the role secrets at start): `SMO_DB_HOST=pgbouncer SMO_DB_PORT=6432 SMO_DB_POOLER=transaction docker compose --profile pooler up -d` puts every module behind it (the `migrate` service stays direct). **`SMO_DB_POOLER`** (`transaction` or `session`) makes a process leave off what a pooler cannot carry: the `options` startup parameter (PgBouncer sets the statement and idle-in-transaction limits itself) and, in transaction mode, server-side prepared statements (**`SMO_DB_PREPARE_THRESHOLD`**: a number, or `off`, overrides). `SMO_DB_HOST` and `SMO_DB_PORT` (default `postgres`, `5432`) are new compose variables. The CI job `compose-pooler` replays the whole runbook through it and `scripts/pooler_check.py` checks that 60 client connections cost at most the pool size and that prepared statements work through this PgBouncer. The README has a section on pool sizing across replicas. On a password rotation, `docker compose restart pgbouncer`. Not done: a pooler in the Helm chart (use your operator's, e.g. CloudNativePG's `Pooler`).
- **Postgres high availability, proved on Kubernetes (PR-DB-7.2 to 7.4, PR-HA-3.2).** The CI job `postgres-ha` installs the CloudNativePG operator (1.25.1, its manifest checked against a sha256), makes a three-instance cluster (`deploy/helm/smo/ci/cnpg-cluster.yaml`, PostgreSQL 17.4 by digest), checks that both replicas stream, installs the chart against it (`ci/cnpg-values.yaml`) and runs the stack's checks. It then force-deletes the primary while `scripts/k8s_failover_probe.py` writes through SME every 250 ms, and requires a new primary, three ready instances again, writes that recover within 90 s, a row committed before the kill on the new primary, a verifying audit chain and the stack's checks passing. A service that always points at the primary (CloudNativePG's `<cluster>-rw`) needs neither. Not covered: a planned switchover, the full runbook replay during the failover, and more than one node (the CI cluster has one).
- **Placement of replicas (PR-HA-5.1).** `placement.mode` (`soft` default, `hard`, `off`) and `placement.zoneKey` in the chart spread a module's pods over nodes (and zones). `soft` is a preference, so nothing changes for a cluster with one node; `hard` leaves a replica Pending rather than put two on one node. The chart's CI checks the rendering of each mode; it does not prove pods land on different nodes (the CI cluster has one).
- **Worker failover, proved on Kubernetes (PR-HA-4.1).** The CI job `helm` queues 100 notifications for a slow destination, force-deletes the worker pods in the middle of the batch, and requires all 100 to be delivered by the replacements (duplicates are counted and allowed).
- **Replicas and rolling restart, proved on Kubernetes (PR-HA-1.1, PR-HA-2.1/2.2).** `deploy/helm/smo/ci/ha-values.yaml` runs two replicas of every module that can have them, and the CI job `helm` now installs with it, checks the stack and the audit chain on two replicas, then restarts every deployment one at a time while a pod in the cluster asks each module for `/health` through its Service. It fails if a call fails twice in a row. Left at one replica: Onboarding and the GUI backend (each holds a volume only one pod may use; their restart is a gap) and the two mock services (in-memory state). Not yet covered: the full runbook replay against replicas (HA-1.2) and calls made with a token while restarting.
- **`moduleDefaults.preStopSeconds` (default 5).** A service pod now waits five seconds after it is marked terminating before it is told to stop, so the Service and its callers stop sending to it first. Set 0 to turn it off.
- **Decision on database high availability (PR-DB-7.1, `docs/adr/0003-postgres-ha.md`).** The one-pod Postgres in the chart stays a lab default and is not highly available. The supported HA route on Kubernetes is an operator (CloudNativePG) behind `postgres.external.*`, a managed service fits the same setting, and compose stays single-node. The lab and failover test follow in this release.
- **Image vulnerability scan (PR-SEC-12.2).** `.github/workflows/image-scan.yml` builds every image the release publishes from the checkout and scans it with Trivy for HIGH and CRITICAL findings that have a fix (`--ignore-unfixed`). It runs when a Dockerfile or a dependency lock changes, every Monday, and by hand (`report_only` to read the findings without failing), writes a report to the job summary (one row per image, then each distinct finding once with where it is) and fails when there is any. An accepted finding goes in `smo/.trivyignore` with its reason. It is not a required check, so a new advisory does not block an unrelated pull request.

### Known limitations
- High availability is proved on a single-node kind cluster. Placement over several nodes and zones is rendered (`placement.mode`), not exercised; a planned Postgres switchover is not tested (only an unplanned primary kill); the rolling restart is probed with `/health` and one retry, not with the runbook replaying through it.
- Onboarding, the GUI backend and the mocks stay at one replica (a volume only one pod may hold, or state in memory); restarting them is a gap by design.
- The bundled one-pod Postgres is a lab default with no backup or HA; for production use an operator or a managed service behind `postgres.external.*` (the CloudNativePG lab in `ci/` is the example). The chart runs no pooler: use your operator's and set `SMO_DB_POOLER`.
- A process reads its database password once: a rotation needs a restart of the module (and `docker compose restart pgbouncer`).
- Compatibility views of moved tables stay in `public` until the next release.
- Carried from 0.3.0: reads are open to every valid token apart from a deny-list (PR-SEC-10); the compose sample rApps are static services with module identities; the audit chain has no GUI view and does not protect against someone who can write the database; the seeded KPIs are over this build's own counters; the O-RAN WG4 YANG models are not bundled (SB-4); the worker exports no metrics.


## [0.3.0] - 2026-10-04

Safer rApps and a second way to run it. An rApp that writes through DME is held by its own safeguards (this was not the case in 0.2.0), the gateway lets an rApp change only what it uses and refuses everything from a stopped one, every change is in a tamper-evident audit chain, a Helm chart installs the stack on Kubernetes, and the operator GUI manages change jobs, KPIs and safeguards. Docker Compose stays the way to run it on one machine.

### Upgrading from 0.2.0
- **Schema**: revisions `0019` (KPI schedules), `0020` (KPI guard) and `0021` (audit chain) are additive; the migration runs as before (the `migrate` service, or the Helm Job). The 0.2.0 code runs on the new schema.
- **R1 Termination now needs the database** (`SMO_DATABASE_URL`, `db_password`), for the audit chain and the kill switch. Compose does this; a deployment of your own must give it the same settings as a module.
- **An rApp may now change only what it uses.** A third-party rApp that calls a route outside the list gets 403 `ROLE_NOT_PERMITTED` (see Changed). Set `SMO_ROLE_ENFORCEMENT=audit` on SME and R1 to log instead while you move it, or add the route to `RAPP_MAY_CHANGE` in `shared/smo_shared/roles.py`.
- **The worker**: compose has a new service, `ran-nf-oam-worker`; the periodic work (staged job advance, KPI schedules and guards) runs only while it does.
- **Mixed versions**: during a rolling upgrade a module that is still 0.2.0 does not forward `X-R1-On-Behalf-Of`, so the DME safeguard fix applies once every module is on 0.3.0.

### Security
- **An rApp that wrote through DME was not held by its own safeguards.** DME mediates an rApp's action (`POST /dme/actions`, the way the SDK and every sample rApp write configuration) and posts the write to RAN NF OAM itself, so RAN NF OAM saw DME as the caller: the kill switch did not stop such an rApp and its limits (config jobs per hour, elements per job, change per write) did not apply, and its jobs were counted against DME. A module now says whom it acts for: `X-R1-On-Behalf-Of`, which `R1Client` adds by itself to every onward call made while handling an rApp's request (so it holds across several modules). R1 Termination forwards it only from an SMO module and drops an rApp's own value, so an rApp cannot pose as another to escape its stop or spend another's allowance. RAN NF OAM applies the safeguards to the rApp, records refusals against it, and counts its jobs. If you run rApps that write through DME and had set limits or a stop, they take effect now. 0.2.0 had this gap; apply this release's gateway and modules together (a mixed-version stack keeps the old behaviour for a call that crosses an old module).

### Changed
- **An rApp may now change only what it uses (PR-SEC-14, v0.3).** The gateway's role policy was a short deny-list; it is now also an allow-list for *changes* (POST, PUT, PATCH, DELETE) by a caller with the `rapp` role. An rApp may change what `smo_sdk` calls (the SDK's own tests fail if a call is off the list), the consumer-facing request routes of the AI/ML services, the `config-jobs` and `rollback` routes of RAN NF OAM (its safeguards apply), and the rApp-facing modules `a1-related`, `ran-analytics`, `dme-push` and `dme-pull`. Everywhere else a change is refused with 403 `ROLE_NOT_PERMITTED`: onboarding, instance management, NFO, FOCOM, the orchestrators, the sample rApps' own APIs, other invokers' registrations, trusted invokers, function/repository/storage administration, sweeps and runtime scaling. **Reads are unchanged** (open to every valid token, apart from the deny-list). SMO modules and the GUI are not affected. An rApp that calls a route outside the list gets a 403 after upgrading: `SMO_ROLE_ENFORCEMENT=audit` counts and logs instead while it is moved, and the route can be added to `RAPP_MAY_CHANGE` in `shared/smo_shared/roles.py`.
- **A stopped rApp changes nothing through the gateway (AI-10.4, extended).** The per-rApp kill switch refused a stopped rApp's *config jobs*; everything else it could still do (publish data, start training jobs, post intents). R1 Termination now reads the switch (`rapp_kill`) and refuses every POST, PUT and PATCH by a stopped rApp, and by an SMO module acting for it (`X-R1-On-Behalf-Of`), with 403 `RAPP_KILLED` before any backend is called, recorded in the audit chain as `REFUSED:RAPP_KILLED` and counted in `smo_role_refusals_total{action="killed"}`. It can still read, DELETE (withdraw what it made), fetch a token, and roll back its own config job. The gateway looks the switch up at most every 3 s per rApp (`R1_KILL_CACHE_SECONDS`), so a switch thrown at RAN NF OAM bites at the gateway within that time (RAN NF OAM's own check for config jobs is immediate). If the database cannot be read the last answer is used for up to a minute, and with none the change is refused (503 `KILL_SWITCH_UNAVAILABLE`). `R1_KILL_SWITCH=off` turns the gateway's part off. The GUI's stop dialog says what a stop now does.

### Added
- **An rApp instance's credentials are delivered to its workload (PR-SEC-14, completing it).** SME keeps only a hash of an invoker's secret, so the secret existed for one moment and had to be fetched by a person and put into the workload by hand. With `RAPP_CREDENTIAL_DELIVERY=kubernetes` (Helm: `rappCredentials.delivery=kubernetes`, default off) rApp Management writes it, when the instance's invoker is made, to a Kubernetes Secret `rapp-<instanceId>-credentials` (`SMO_INVOKER_ID`, `SMO_INVOKER_SECRET`, `SMO_IDENTITY_KIND=rapp`) for the workload to take with `envFrom`; rotating (`POST /instances/{id}/credentials`) replaces it and answers with the Secret's name instead of the secret, and terminating deletes it. If it cannot be written, creating the instance fails with 503 and the invoker is withdrawn. In the chart the rApp Management pod, and only it, has a service account (token projected, not auto-mounted) whose Role can create, update and delete Secrets in the namespace and read none; CI checks this on kind. Compose has no equivalent (its sample rApps are static services with module identities). `scripts/k8s_credential_delivery_check.py` is the in-cluster check.
- **Tamper-evident audit of changes (PR-SEC-11).** The gateway records every authenticated POST, PUT, PATCH and DELETE in a hash chain (`audit_log`, `audit_head`, revision `0021`): who (the invoker id and role; for an SMO module acting for an rApp, the module with the rApp in `detail`), what (method and path, never the query or the body), the result (the status, or `REFUSED:ROLE_NOT_PERMITTED`) and the correlation id. A row that is edited, deleted, inserted or cut from the end is found by `python -m smo_shared.audit verify` (exit 1 and the first broken row); `export [--since SEQ] [--format jsonl|syslog]` writes the rows and a closing `head` line to keep outside the database. Reads, unauthenticated calls and rate-limited calls are not recorded. **R1 Termination now needs the database** (`SMO_DATABASE_URL`; compose gives it the password secret and starts it after the schema): a database that is down fails no call, it is counted in `smo_audit_writes_total{outcome="failed"}` and logged; `R1_AUDIT=off` turns recording off. Not done: the BFF/GUI view (SEC-11.6), and the chain does not protect against someone who can write the database *and* recompute every hash (keep the exported head elsewhere).
- **A Helm chart** (`smo/deploy/helm/smo`, PR-OPS-2): the same stack as `docker-compose.yml` on Kubernetes, which stays the way to run it on one machine. One template over a `modules` map gives each module a Deployment and a Service (named as in compose, so one release per namespace), probes from `/live` and `/ready` (a heartbeat file for the worker), the hardened pod settings of PR-SEC-13, secrets as files under `/run/secrets` (an rApp never gets the enrollment secret), and optional Ingress, NetworkPolicy (the mock Near-RT RIC isolation), PodDisruptionBudget and HorizontalPodAutoscaler. **The database**: a bundled one-pod Postgres by default, or `postgres.enabled=false` with `postgres.external.*` for a managed one. **Migrations (PR-OPS-3)**: a Job runs `scripts/migrate.py` on install and as a `pre-upgrade` hook, so a failed migration aborts the upgrade with the old pods still serving; every module waits for the schema in an init container (`migrate.py --wait SECONDS`, new) and never serves on an older one. CI installs the chart on kind from images built from the checkout, runs the compose smoke scripts inside the cluster, upgrades it and uninstalls it. `tests_integration/test_helm_chart.py` keeps chart and compose in step. Not in the chart: `netconf-lab`, `edge-tls` (use the Ingress). Multiple replicas of a module, load balancing and HA remain the next release's work.
- Change management in the operator GUI. The config-job drawer (Infrastructure, O1 endpoints & jobs) now shows a staged job's waves and why it is halted, and an operator can **Continue**, **Halt** or **Abort** a halted job; **Roll back…** previews what would be written and which values were changed after the job wrote them, and overwrites those only when the operator chooses "Roll back anyway"; a job's KPI guard and what it found are shown. The "New CM write" form takes an optional staged rollout (wave size, pause, alarm gate, halt or undo on a failed gate) and an optional KPI guard. The KPIs page has a **KPI definitions** tab: define, edit and delete KPIs, add the standard set, and manage the schedules that publish a KPI to DME with what the last run did. Operators may drive and roll back jobs (attributed to them; an admin holds the MSAC tier, as for a new write); KPI definitions and schedules are admin-only. The GUI backend deliberately does not expose `kpi-check`, `publish` or `advance-due`.
- Safeguards page in the operator GUI: per rApp instance, whether it is stopped (and by whom and why) and its limits with the hourly use; **Stop** (an operator may; the reason is kept and the action is attributed to them), **Resume**, **Limits…** and **Remove limits** (admin); every refusal recorded, filterable by rApp and reason; and who is told about refusals (add and remove watchers, admin). `GET /rapp-mgmt/instances/{id}/safeguards` reads an instance's stop state and limits in one call (503 when RAN NF OAM cannot answer, never "not stopped"; a terminated instance has no credential and shows nothing). The GUI backend allows these calls: stopping at operator level, everything else that changes a safeguard at admin level.
- A worker for periodic work (PR-MSG-4): `python -m smo_shared.worker` runs a module's `app/tasks.py` as its own process (the same image; compose service `ran-nf-oam-worker`), so a request process never runs a timer. Run as many workers as you like: a task runs at most once per interval across all of them, and a worker that dies frees its tasks for another. A task that fails is logged and retried after `SMO_WORKER_FAILURE_BACKOFF_SECONDS` (default 30); `SMO_WORKER_TICK_SECONDS` (default 5) is how often a worker looks. It has no port: its healthcheck reads a heartbeat file. RAN NF OAM's worker does three things: it **advances staged CM jobs** whose pause between waves has elapsed (what `POST /config-jobs/advance-due` did when called), **publishes scheduled KPIs**, and **purges old refusal records**. Without a worker none of these happens by itself; the routes still work when called.
- KPI guard on a CM job (PR-MSG-4, completing AI-10.5): `POST /ran-nf-oam/config-jobs` takes `kpiGuard` (`kpi`, `baselineMinutes`, `observationMinutes`, `maxRegressionPercent`, `direction`, `minSamples`, `revert`, `msacRole`; ignored by a dry run, 404 for an undefined KPI). Once the observation window has passed, the worker runs the check of `POST /config-jobs/{id}/kpi-check` with those settings and, when `revert` is set, rolls back the elements that regressed with a rollback job (`requestedBy` `kpi-guard:<original requester>`). The revert is never forced: if a later change has altered what the job wrote, nothing is reverted and the job says so. `GET /config-jobs/{id}` shows `kpiGuard`, `kpiGuardResult` and `kpiGuardCheckedAt`. A verdict of OK or REGRESSED is final; too little data is tried again each minute until `RAN_NF_OAM_KPI_GUARD_GRACE_MINUTES` (default 60) after the window, then final. Only finished jobs (COMPLETED or PARTIAL_SUCCESS) are guarded. Schema revision `0020` (three nullable columns on `write_config_job`).
- KPI schedules: `PUT /ran-nf-oam/kpi-schedules/{id}` (`kpi`, `intervalSeconds` 60 to 86400, `lookbackSeconds` default the interval, `groupBy`, `managedElementRef`, `cellId`, `enabled`) publishes a KPI to DME every interval, as `POST /kpis/{name}/publish` does; `GET` lists them and says what the last run did (`lastRunAt`, `lastStatus`, `lastDetail`, `nextRunAt`); `DELETE` removes one. A run that fails is marked `ERROR` on the schedule and waits for its next interval. `PUT`/`DELETE` are internal-only at the gateway. Schema revision `0019` (`kpi_schedule`).
- Refusal records can be purged: `POST /ran-nf-oam/safeguard-refusals/purge` (`older_than_days`, or `SAFEGUARD_REFUSAL_RETENTION_DAYS`; 422 with neither, so a purge never runs without an age) and the worker purges daily when the variable is set. Default `0` keeps everything. Internal-only at the gateway.

### Added
- Standard KPIs and KPIs in DME (MGT-11.6, 11.7): `POST /ran-nf-oam/kpi-definitions/standard` defines six KPIs that are not defined yet (`dl_prb_utilization`, `rrc_connected_ues_mean`, `dl_ue_throughput`, `handover_failure_rate`, `handover_success_rate`, `handover_ping_pong_rate`) and keeps one an operator has edited; `GET` lists them without writing. They are over the counters this build carries, not the TS 28.554 definitions, which are not reproduced. `POST /kpis/{name}/publish` computes a KPI as `GET /kpis/{name}` does and delivers one record per group to every DME data job open on the type `RAN.KPI.<name>` (registered as RAN NF OAM's production capability), so an rApp reads a KPI as it reads any other data. Nothing runs it on a schedule. Both are internal-only at the gateway. A KPI cannot be named `standard`.
- Events for refusals (AI-10.6): every time the platform refuses an rApp (the kill switch, the rate, the blast radius or the magnitude limit) the refusal is recorded (`GET /ran-nf-oam/safeguard-refusals`, filters `invoker_id`, `code`, `since`) and announced through the outbox to each subscriber of `POST /ran-nf-oam/safeguard-subscriptions` (`callbackUri`, optional `refusals` to narrow it): `eventType` `RAPP_SAFEGUARD_REFUSAL` with `refusal`, `invokerId`, `requestedBy`, `detail`, `occurredAt`. The same refusal of the same rApp is announced once per `SAFEGUARD_EVENT_MIN_INTERVAL_SECONDS` (default 60; 0 announces every one) but every one is recorded, so a looping rApp cannot flood its watchers. Subscriptions and the record are internal-only at the gateway (they name other rApps). Schema revision `0018` (`safeguard_subscription`, `safeguard_refusal`). Refusals are not purged yet.
- Blast radius and magnitude limits (AI-10.3): the manifest's `limits` also takes `maxElementsPerJob` (managed elements one job may touch) and `maxChangePercent` (how far a numeric value may move in one write, in percent of its current value), pushed to RAN NF OAM with `configJobsPerHour` at bootstrap. `PUT /rapp-limits/{id}` now takes any of the three (at least one; it replaces the set). `POST /config-jobs` from an rApp with such a limit answers 403 `RAPP_BLAST_RADIUS_EXCEEDED` or `RAPP_MAGNITUDE_EXCEEDED` before anything is recorded or sent, dry runs included; the current value is read from the NF, and a value that cannot be read or is not a number cannot be measured and is refused too. Rollbacks and reverts are not limited. Schema revision `0017` (`rapp_limit`).
- Per-rApp kill switch (AI-10.4): `PUT /ran-nf-oam/rapp-kill/{invokerId}` (`requestedBy`, `reason`) stops an rApp: its `POST /config-jobs` (dry runs too) answer 403 `RAPP_KILLED`, and a job of its that waits between waves does not `continue`. Rollback, revert, halt and abort still work, because undoing must never be refused. `DELETE` lifts it, `GET /rapp-kill[/{id}]` reads it. rApp Management offers it per instance (`PUT`/`DELETE /instances/{id}/kill`, which uses the instance's `oauthClientId`; 503 when RAN NF OAM cannot be told). All of these are internal-only at the gateway (an rApp cannot stop or free another rApp; it may read whether it is stopped itself). Schema revision `0016` (`rapp_kill`).
- Caller roles at the gateway (PR-SEC-14). Before, any valid token reached every route behind R1, and an rApp's token was indistinguishable from an SMO module's (both asked for the same scope). Now SME records every invoker as `internal` (it presented the enrollment secret, `X-SMO-Enrollment`: a new compose secret, `secrets/enrollment_secret`, mounted by SME and every SMO module, never an rApp) or `rapp`; the `smo-internal` and `smo-gui` scopes go to `internal` invokers only (an rApp asks for `smo-rapp`); introspection reports the `role`; R1 Termination forwards it as `X-R1-Role` (a caller-supplied value is dropped) and refuses an rApp (403 `ROLE_NOT_PERMITTED`) on a deny-list of internal-only routes: `PUT`/`DELETE /ran-nf-oam/rapp-limits/{id}`, `PUT`/`DELETE /ran-nf-oam/kpi-definitions/{name}`, `POST /ran-nf-oam/config-history/purge`. Every other route is open to every valid token, as before; the list is `INTERNAL_ONLY` in `smo_shared/roles.py`, and a test fails if an entry names a route that no longer exists. `SMO_ROLE_ENFORCEMENT` is `enforce` by default and `audit` for a rolling upgrade (counted and logged, then allowed). SME refuses a wrong enrollment secret (403) and, with none configured, registration (503 `ENROLLMENT_NOT_CONFIGURED`) unless `SME_ALLOW_OPEN_ENROLLMENT` is set. Sample rApps run as `SMO_IDENTITY_KIND=rapp`. Schema revision `0015` (`invoker_registration.kind`; existing invokers stay `internal`).
- rApp Management registers an SME invoker for every rApp instance at create (no enrollment secret: an rApp's role), and the id is the instance's `oauthClientId` (before, a random UUID that matched no token). `POST /instances/{id}/credentials` issues the client id and secret once, in that answer only (`Cache-Control: no-store`), and rotates them on a repeat while the instance is DEPLOYING; terminating the instance deregisters the invoker. This is what makes the per-rApp limit of AI-10.2 apply to the rApp that holds the credentials: with the random UUID it keyed on, it never could.
- CI: the job "Upgrade from the previous release keeps its data" (`scripts/check_upgrade_from_previous_release.sh`) installs the newest final `smo-v*` release from its own source, puts data into it with its own demo runbook, stops it and starts this commit's stack on the same database, so this commit's `migrate` service upgrades real rows. It then checks that every table kept its rows (but the outbox and idempotency keys, which come and go), that the packages and instances are the same by id, and that the upgraded stack answers. Its control seeds a migration that passes on an empty database and fails on one with packages in it; the upgrade must refuse it and leave the schema revision as it was. Runs when a pull request changes `smo/migrations` or the check, and on every push to `main` (OPS-10.5).
- Link types in the topology: `GET /topology/links` lists the neighbour relations declared in the cell guards, each as `INTRA_ELEMENT` (both cells on one managed element), `INTER_ELEMENT`, `AMBIGUOUS` (several elements claim the neighbour's cell id; not guessed) or `EXTERNAL` (no managed element has it), with `reciprocal` (the other side declares it back), `sameSectorGroup` and `sameIncidentZone`; filters `managed_element_ref` (either end) and `link_type`. `GET /topology/relation?a=<DN>&b=<DN>` says how two managed objects stand in the containment tree: `SAME`, `ANCESTOR`, `DESCENDANT`, `SIBLING`, `SAME_ELEMENT` or `DIFFERENT_ELEMENT` (404 `MANAGED_OBJECT_NOT_FOUND` for a DN that is not in the tree). The names are this build's own, not the TEIV RAN domain model (MGT-10.2).
- Per-rApp limits: the manifest may declare `limits: {configJobsPerHour: N}` (under `rappManifest` or at the top level; a whole number from 1 to 100000; an unknown limit name or a bad value fails onboarding). When an instance finishes bootstrapping, rApp Management hands the limit to RAN NF OAM under the instance's OAuth client id (`PUT /rapp-limits/{invokerId}`; `GET` also says how many jobs the rApp started in the last hour; `DELETE`), and `POST /config-jobs` answers `429 RAPP_RATE_LIMITED` with `Retry-After` once that caller has started N jobs in the last hour. The push fails closed: a package that declares a limit that RAN NF OAM does not accept stays `DEPLOYING` and `bootstrap-complete` answers 503 until it can be retried. Rollbacks, automatic reverts and dry-runs are not counted or refused. A caller cannot change its own limit (403 `RAPP_LIMIT_SELF_CHANGE`); the limit is removed when the instance is terminated. Schema revision `0014` (`rapp_limit`, `write_config_job.invoker_id` and `created_at`, `rapp_instance.rapp_limits_set`) (AI-10.1, AI-10.2).
- Revert on a KPI regression: `POST /config-jobs/{jobId}/kpi-check` (`kpi`, `baselineMinutes`, `observationMinutes`, `maxRegressionPercent`, `direction` `higher`/`lower`, `minSamples`, `revert`, `force`) compares a KPI over the window before the job with the window from the job on, for each element the job changed. A change worse than `maxRegressionPercent` is `REGRESSED`; with `revert` the regressed elements (only those) are rolled back with a rollback job (access check and changed-since guard as for `/rollback`). Too few samples, an undefined KPI or a zero baseline is `INSUFFICIENT_DATA` and nothing is reverted. It is a check to call, not a watcher: nothing runs it on a schedule (AI-10.5).
- KPIs: `PUT /kpi-definitions/{name}` defines a KPI as a formula over PM counters (`formula`, and `counters`: which counter feeds which variable and how its samples are combined, `sum` `avg` `min` `max` `last` or `count`), `GET /kpi-definitions[/{name}]`, `DELETE`. The formula language is arithmetic, comparisons, `min` `max` `abs` `sqrt` `round` `log10` and `ifelse(condition, then, else)`; it is parsed, never evaluated by Python, and anything else (attribute access, other calls, strings, comprehensions, huge exponents) is refused when the KPI is defined. `GET /kpis/{name}?from_time=&to_time=&group_by=cell|element|sectorGroup|incidentZone|all&managed_element_ref=&cell_id=` computes it from the PM files RAN NF OAM has stored: counters are combined per group and the formula evaluated over the results, so a region's success rate is its summed successes over its summed attempts. A group with no data, or a division by zero, has a null `value` and a `reason` (`NO_DATA`, `UNDEFINED`). At most `RAN_NF_OAM_KPI_MAX_FILES` (default 2000) of the newest files are read, and the answer says `truncated`. Schema revision `0013` (MGT-11.1-11.5).
- Staged rollout of a CM job: `POST /config-jobs` takes `waveSize` (elements per wave; every change of one element goes in the same wave), `wavePauseSeconds`, `gateMaxNewAlarms` and `onGateFailure` (`halt` or `revert`). After each wave but the last a health gate runs: a rejected sub-change, or more than `gateMaxNewAlarms` new critical or major alarms on the wave's elements since it started, fails it. A failed gate leaves the job `HALTED` (`haltedReason` `GATE_FAILED`, the later waves still `PENDING`), or with `revert` undoes the applied waves with a rollback job and ends the job `FAILED` (the undone sub-changes are `REVERTED`, the waves that never ran `REJECTED` `WAVE_NOT_RUN`; if the revert is unsafe or incomplete the job halts `REVERT_REFUSED`). `POST /config-jobs/{id}/continue` (a pause not yet elapsed is 409 `WAVE_PAUSE_NOT_ELAPSED` unless `force`), `/halt`, `/abort` and `POST /config-jobs/advance-due` (for a scheduler: runs the jobs whose pause has elapsed) drive a halted job; `GET /config-jobs/{id}` shows `waveCount`, `currentWave`, `haltedReason`, `nextWaveAt` and each sub-change's `wave`; a dry run lists the waves. A job without `waveSize` is one wave and behaves as before. Schema revision `0012` (MGT-5.1-5.5).
- CM rollback: `POST /config-jobs/{jobId}/rollback` (`requestedBy`, optional `accessScope`, `msacRole`, `force`, `dryRun`) undoes a job with a new write job built from its snapshots, in reverse order, restoring the recorded before values (a deleted object is created again, a created one deleted). It goes through MSAC, the schema check and dispatch like any write; the new job's `requestedBy` is the actor and `GET /config-jobs/{id}` shows `rollbackOf` and `rollbackForced`. If what the job wrote has been changed since, the answer is 409 `CONFIG_CHANGED_SINCE` unless `force` is set (the new job then says `rollbackForced`); `dryRun` returns the plan and every difference. An attribute that had no value before the write, a missing before image, or purged snapshots make it 422 `ROLLBACK_NOT_POSSIBLE` with the reason. Schema revision `0011` adds the two columns to `write_config_job` (MGT-1.6, 1.7).
- `GET /managed-entities/{ref}/config-history/diff?from_snapshot=&to_snapshot=` compares two snapshots of one managed object: attributes whose values differ, and attributes only one of them touched (MGT-1.5).
- `POST /config-history/purge` deletes CM snapshots older than `older_than_days` (default `RAN_NF_OAM_CM_SNAPSHOT_RETENTION_DAYS`, `0` = keep for ever, so no upgrade deletes anything; the route refuses to run with no age). Jobs and sub-changes stay; a job whose snapshots were purged can no longer be rolled back (MGT-1.8).
- `scripts/rotate_db_password.sh` rotates the compose stack's database password (new value, `ALTER ROLE`, `secrets/db_password`, recreate every service); `docs/SECRETS.md` has a rotation runbook for each secret an operator can rotate (database password, O1 adaptor credentials and client certificates, a module's SME invoker secret, the GUI signing key), each tried once in CI or a test (SEC-4.8).
- `.github/workflows/release-images.yml`: pushing a `smo-v*` tag (or running it by hand with an existing tag) builds every service image, pushes `ghcr.io/<owner>/<repo>/smo-<module>:<version>`, signs each by digest with cosign (keyless), attaches build provenance and an SBOM, and writes release notes (this changelog's section plus the merged PR titles) onto the GitHub release. The verification command is in `docs/RELEASES.md` (OPS-4.2, 4.3, SEC-12.3, 12.4).

A reference that names no configured credential, or a pasted secret, is refused at registration without being echoed. Endpoints without a reference keep using `NETCONF_SSH_PASSWORD` (SB-2.1, 2.2, SEC-4.6).
- `?datastore=candidate` on an ssh adaptor URI: each CM write is one transaction on the candidate datastore (lock, edit-config, commit, unlock); a refused edit or commit is followed by discard-changes, a refused lock changes nothing, and the step that failed is named in `rejectionDetail`. A server without `:candidate:1.0` is refused before anything is sent. Per write, not per job (SB-1.8).
- Writes to a model-based NETCONF server: with `?model=smo-lab` on the ssh adaptor URI, `POST /config-jobs` sends an `edit-config` on the model's list entry (`operation` as `nc:operation`, key leaf, kebab-case leaves) instead of the `<managed-object>` shape (SB-1.6). A refused change now carries the server's own `<rpc-error>` as `rejectionDetail` on `GET /config-jobs/{id}` (tag, path, message; `rejectionReason` stays `NETCONF_RPC_FAILED`); new column `write_config_sub_change.rejection_detail`, schema revision `0006` (SB-1.7).
- `/metrics` now also counts outbound calls: `smo_outbound_calls_total{client,target,method,outcome}` and `smo_outbound_call_duration_seconds{client,target}`. `client=r1` is a call through R1 Termination (`target` is the module, `outcome` is `2xx`..`5xx`, `timeout` or `error`); `client=webhook` is a callback to a registered destination (`target=callback`, plus `outcome=blocked` when the SSRF guard refused it). Callback hosts are deliberately not a label (OBS-2.6).
- A model-based NETCONF server can be read: register the ssh adaptor with `?model=smo-lab` on its URI (`ssh://netconf@host:830?model=smo-lab`) and `GET /managed-entities/{ref}/config` sends a subtree `get-config` on that YANG model and returns its leaves as camelCase attributes; without `?model=` the `<managed-object>` shape is sent as before. Writes to such an endpoint are refused until SB-1.6 (SB-1.5).
- `R1_PUBLIC_BASE_URL`: with the TLS profile, set it to the HTTPS door (for example `https://localhost:8443`) and `/bootstrap` advertises `https://.../sme/...` addresses, with the OAuth2 token endpoint forwarded by the edge, instead of `http://sme:8000`; unset, nothing changes (SEC-1.6).
- `/metrics` now also carries `smo_fsm_transitions_total` and `smo_fsm_illegal_transitions_total` (every lifecycle state change, by machine, state and event) and the database pool gauges `smo_db_pool_connections{state}` and `smo_db_pool_capacity` (OBS-2.4, 2.5).
- `docker compose --profile netconf-lab up -d netconf-lab`: a real NETCONF-over-SSH server (Netopeer2) with a small model, on `127.0.0.1:8830`, for trying the SSH transport (`netconf-lab/README.md`; development only) (SB-1.4).
- CM change history: every dispatched write records the values it replaced and the values it wrote (`cm_snapshot`, schema revision `0004`); `GET /managed-entities/{ref}/config-history` lists them. Each write now makes one extra read of the NF first (up to 30 s on an unresponsive one); `RAN_NF_OAM_CM_SNAPSHOTS=false` turns it off (MGT-1.1–1.4).
- `dryRun: true` on `POST /config-jobs`: every check runs, nothing is sent or stored, and the response says per change whether it would pass (MGT-3).
- NETCONF over SSH to an O1 adaptor: register it with `transport: ssh` and `adaptorUri` `ssh://user@host[:port]`; CM writes and `GET /managed-entities/{ref}/config` then use RFC 6242 sessions. Set `NETCONF_SSH_KNOWN_HOSTS` and `NETCONF_SSH_PASSWORD` (or `_FILE`) / `NETCONF_SSH_KEY_FILE` for RAN NF OAM. Schema revision `0003` adds `o1_adaptor_endpoint.transport` (default `http-mock`) (SB-1.1–1.3).
- Structured JSON logs on stdout in every service, one access line per request with the route template, status and duration, secrets scrubbed; `LOG_LEVEL` (#207).
- `GET /metrics` in every service (Prometheus): request count and latency by method, route template and status. Container network only: R1 Termination and the TLS edge do not forward it (#208).
- Alembic schema migrations: baseline revision `0001` is `migrations/001_init.sql`; `python scripts/migrate.py` upgrades, and stamps a database that was created from the file (#209).
- Optional TLS edge (`docker compose --profile tls up`, nginx on `3443` and `8443`, development certificates from `scripts/make_dev_certs.sh`) (#206).
- Secrets inventory (`docs/SECRETS.md`), `*_FILE` variants for secrets, and the database password as a compose secret (`scripts/init_secrets.sh`) (#205).
- Request body cap (`R1_MAX_BODY_BYTES`) and a per-caller rate limit (`R1_RATE_PER_SECOND`, `R1_RATE_BURST`) at R1 Termination (#204).
- Database backup and restore scripts (`scripts/db_backup.sh`, `db_restore.sh`) (#200); slow-statement log in compose (`POSTGRES_SLOW_QUERY_MS`) (#201).
- Route-table authorisation walk: every backend route is refused without a valid token (#202).
- Liveness and readiness probes (`/live`, `/ready`; `/health` kept), single-runner guard for periodic work, idempotency keys on command routes, optimistic concurrency on lifecycle rows, one SME identity per module across replicas, connection pool limits and graceful shutdown (#190–#198).

### Changed
- **Every service's root filesystem is read-only**, with `/tmp` as a memory-backed scratch directory (SEC-13.2). The runbook copies rApp CSARs into the new `smo_scratch` volume at `/srv/scratch` on `r1-termination` instead of `/tmp`; if you had your own `docker compose cp ... :/tmp/...` step, point it there. A service that wrote anywhere else would now fail loudly.
- DME's stop-job request to each producer (when a data job is deleted) is written to the transactional outbox in the same transaction as the deletion and sent after it commits, so a crash no longer leaves a producer running a deleted job; at-least-once, so a producer may see the DELETE twice. Schema revision `0005` adds `notification_outbox.method` (default `POST`) (MSG-1.10).
- `PATCH /alarms/{id}/ack` and `/clear` return 404 `ALARM_NOT_FOUND` for an unknown alarm (they failed with a 500), and `new_state` must be `ACKNOWLEDGED` or `UNACKNOWLEDGED` (422 otherwise) (MGT-8.1).
- **CM writes are checked against each leaf's type and constraints before anything is sent.** A write with an out-of-range number (`localPortNumber` 70000), the wrong type, a string over its length or off its pattern, or too many decimals is refused with 422 `SCHEMA_VALIDATION_FAILED` and a reason, for vendors whose data model comes from the bundled WG10 / WG5 YANG or the 3GPP NR NRM descriptors, or from a descriptor you load; before, only unknown attributes and enum values were refused (SB-5).
- DME's type-change, offer-termination and job-push notifications are written to the transactional outbox in the same transaction as the change and sent after it commits, so a crash no longer loses them; delivery is at least once, so a consumer may see one twice after a crash (#MSG-1.5).
- SME's CAPIF event notifications (service and invoker events) use the same outbox, with the same at-least-once delivery (MSG-1.6).
- AI/ML Workflow's job-completion and model-performance notifications use the outbox too, committed together with the completion or report they announce (MSG-1.7).
- A1 Related, FOCOM (inventory, alarm and performance) and MDAF notifications use the outbox as well. An MDAF report, its subscriber notifications, threshold state and request deliveries are now one transaction (MSG-1.8).
- Intent Service (RMIH, report and autonomy-operator notifications) and RAN NF OAM (PM-file ready) use the outbox, which completes it: every notification to a registered destination, except the DME stop-job DELETE, is now durable. An autonomy dispatch and the Intent it creates are one transaction (MSG-1.9).
- The bundled O-RAN WG10 and WG5 YANG descriptors now include the attributes of the 3GPP common groupings (`id`, `userLabel`, the EP and managed-function attributes), so a CM write to those classes may set them; four port-number attributes are `integer` instead of `any` (SB-3).
- **The schema is created and upgraded by a `migrate` service**, which every service waits for; Postgres no longer mounts `001_init.sql`. A kept volume is stamped and upgraded on the next `docker compose up -d --build`; an empty one is built from the baseline. Schema revision `0002` adds the `notification_outbox` table (additive).
- **Database credentials have no default.** Services refuse to start without `SMO_DATABASE_URL`; compose reads the password from `secrets/db_password` (run `scripts/init_secrets.sh` first). A Postgres volume created with the old default password keeps it: recreate the volume (#199, #205).
- Containers run as a non-root user with all capabilities dropped; NFO no longer runs privileged and no longer mounts the Docker socket. Volumes created by an earlier stack are root-owned: recreate them (#203).
- The Dockerfile's plain-text uvicorn access line is off; the structured access log replaces it (#207).
- The migration CI job and `CLAUDE.md` step 4 create the schema with `scripts/migrate.py` instead of applying the SQL file directly (#209).
- The hello-world sample rApp and its CSAR are removed. The demo runbook (§0–§23), the integration tests and the GUI's onboard-form hint use the Energy Saving package instead.

### Upgrade notes
- `docker compose up -d --build` runs the migrations (`docker compose logs migrate`); outside compose run `python scripts/migrate.py`. A database created from `001_init.sql` by an earlier stack is stamped at `0001` first. Take a backup (`scripts/db_backup.sh`) before upgrading; `python scripts/migrate.py --downgrade -1` reverses one revision.
